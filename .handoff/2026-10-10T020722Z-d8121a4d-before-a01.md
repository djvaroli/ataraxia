## Decisions and constraints

- This is a personal side project. Use modular code, composition, clean protocols,
  concise documentation, focused unit tests, and a few Docker integration checks.
  Avoid production-scale machinery and repeated questions about routine choices.
- Proposed stack: React/TypeScript/Vite frontend, FastAPI API, Redis as the
  persistent initial database, nginx, and Docker Compose. Keep frontend/backend
  concerns separate and the API independent of slow discovery generation.
- User clarification: Firebase email/password sign-in for an account they manually
  provision. Disable end-user sign-up; verify tokens and the configured owner UID
  on the backend. Google redirect/auth-helper setup was rejected as unnecessary.
- Habit behavior includes selected weekdays, dated completion, undo/backfill,
  calendar circles, weekly consistency, and small milestones. The supportive
  motivation style is a design default; the earlier optional preference question
  had no answer and is not a blocking decision.
- Discoveries use source-backed LLM selection/explanation and automatic stable
  history, with favorites separate from saving. Paper limitations are conditional
  on evidence; artwork context may be shorter when only metadata is available.
- Run one sequential worker with bounded attempts and call/token caps. Keep simple
  restart recovery and atomic publication; no distributed job leases or monetary
  reservation ledger.
- Local Redis persistence is needed from the start. Daily GCP backups with 30-day
  retention and a restore drill are deferred until before regular personal use.
  GCP/Firebase resources, credentials, and configuration must be separate from Osmy.
- Provider/model, personal budget, owner UID/time zone, dedicated cloud project,
  and host/domain remain setup choices. They do not block foundation work with
  fixtures. Do not create resources just because they appear in the design.
